# Module 04 — Interviewer Q&A

**1. Why hybrid fan-out instead of picking one strategy for everyone?**
Fan-out-on-write alone would mean a single celebrity post (100M+ followers) triggers tens of millions of `feed_items` writes in seconds — a spike no capacity plan can absorb (Module 01's Trade-offs table). Fan-out-on-read alone would mean the dominant read path (~115,000 reads/sec average, Module 00's Capacity Estimation) pays a live follow-graph merge on every single feed load, even though the overwhelming majority of accounts have a few hundred followers and are cheap to precompute. The `CELEBRITY_THRESHOLD` branch in `PostService.createPost` (Module 02) lets each post pay whichever cost — write-time or read-time — actually matches its author's follower-count shape.

**2. Why do stories get their own `story_items` table instead of reusing `feed_items` with a nullable `expires_at`?**
Both tables share the exact same partition/clustering shape on purpose (Module 03) — the Fan-out Worker's write logic doesn't fork into two implementations. But they differ in storage engine: `feed_items` lives in Redis + Cassandra because a feed entry is meant to persist; `story_items` lives in Redis alone, with `expires_at` as a genuine TTL the store enforces via `EXPIRE` (Module 01's Trade-offs table). Folding a 24-hour-TTL row type into the same Cassandra table as permanent feed rows would mean paying Cassandra's durability cost for data engineered to be deleted in a day, and would trade an automatic store-level guarantee for a cleanup job that has to be written, scheduled, and trusted not to fall behind.

**3. Why does a follower see a freshly posted photo before transcoding has even finished?**
Because fan-out writes reference the *original* upload URL immediately, not a transcoded variant (Module 01's Media path). Transcoding and fan-out are two independent Kafka consumer groups reading the same `post-created` event, so a slow transcode job never blocks or delays the fan-out write. If media availability gated the post from appearing until transcoding finished, one slow high-resolution video would delay every follower seeing the post, not just the poster.

**4. Why does the Media Worker produce thumbnail/feed/full-res variants once at write time instead of transcoding on demand per request?**
Reads outnumber writes by roughly 100x here — ~115,000 feed reads/sec average against ~1,150 post writes/sec (Module 00's Capacity Estimation). Transcoding once per post and serving the results from [object storage behind a CDN](../../hld-building-blocks/cdn.md) means that cost is paid a fixed number of times per post; transcoding on demand would mean repeating the same expensive CPU/GPU work — or building an ad hoc cache for it — on every one of the millions of times that post gets viewed.

**5. Why is `follows` keyed `(followee_id, follower_id)`, not the other way around?**
Because the query the entire fan-out mechanism depends on is "list every follower of account X," run once per post by the Fan-out Worker (Module 03). Keying `followee_id` first makes that a single-partition range scan. "Who does X follow" — the query the celebrity live-merge path needs — is real but far lower volume, so it gets a secondary index (`follows(follower_id)`) instead of shaping the primary key around it.

**6. Why not use a graph database for the follow graph, since "who follows me" sounds like an inherently graph problem?**
Because this system never runs a multi-hop traversal against the follow graph — the only query is "list all followers of X," a single hop, answered by one indexed partition read on a relational table (Module 01's Trade-offs table). A graph database's real strength, efficient multi-hop traversal (mutual followers, degrees of separation), is never exercised here, so adopting one would add operational surface area without a query to justify it.

**7. Why is `author_id` denormalized onto `feed_items` and `story_items` instead of joined from `users` at read time?**
Rendering a feed page needs the author's username and avatar for every item, and this path runs at ~115,000 reads/sec (Module 03). Without `author_id` sitting directly on the fan-out row, every feed render would need a join or a second round-trip back to `users` per item — at that volume, that's the difference between one store lookup and one-plus-N per page.

**8. Why is `FanoutStrategy` decided once per post at write time instead of being re-evaluated per follower or at read time?**
`PostService.createPost` picks `WriteFanoutStrategy` or `ReadFanoutStrategy` a single time, based on the author's `follower_count` at the moment of posting (Module 02) — the strategy describes how *this post* reaches followers, not a per-follower decision, so there's nothing to re-evaluate per follower. Deferring the choice to read time would mean every reader independently re-deriving the same author's follower count on every feed load, for a decision that only needs to be made once and doesn't change for the life of that post.

**9. What happens to a post's fan-out entries if the post is deleted while fan-out is still mid-flight?**
The delete sets the post row's status rather than trying to cancel or claw back fan-out writes already in flight (Module 01's Concurrent-User Handling). `FeedService` silently skips any `feed_items` entry whose `post_id` no longer resolves to a live post — the same lazy-cleanup approach this guide's [News Feed System](../news-feed-system/04-interviewer-qna.md) case study uses for its own deletion question. Followers who already received the fan-out entry simply don't see it rendered; no explicit fan-out-cancellation message needs to exist.

**10. What happens to a feed read when the Feed Store (Redis + Cassandra) is unreachable?**
`FeedService.getFeed` catches the `feed_items` lookup failing specifically and falls back to the same live-read-and-merge path already used for celebrity accounts, for the entire request — trading latency for availability rather than surfacing a 500 (Module 02's Error cases, Module 01's Load Handling). The celebrity live-merge lookup itself is separately wrapped in a [circuit breaker](../../scalability-resilience/circuit-breakers-retries.md) against Core DB, so a degraded Core DB drops celebrity posts from the merge temporarily rather than failing the whole feed request.
