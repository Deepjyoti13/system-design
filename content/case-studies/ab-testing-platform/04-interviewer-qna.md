# Module 04 — Interviewer Q&A

**1. What happens when two requests hit the same resource at the same instant?**
Two shapes of this race show up here. Assignment: two app-server instances computing a variant for the same `(experiment_id, user_id)` at once independently compute the identical hash and land on the identical variant — there's nothing to race over, the same "consistency by determinism, not coordination" property this guide's feature-flag design relies on. Exposure logging: two exposure events for the same `(experiment_id, user_id)` racing (a double-render, a client retry) resolve at the unique constraint on `exposures(experiment_id, user_id)` — the second insert is a no-op, and only the first exposure's variant and timestamp are kept.

**2. What happens when traffic spikes 10x for an hour?**
Assignment is unaffected — it's an in-process function call, so it scales exactly as far as whatever service is experiencing the spike already scales, with zero additional load on this system's own infrastructure, per Module 01's Load Handling. The real pressure lands on exposure and conversion ingestion, which backs up in a partitioned queue rather than dropping events; a growing queue depth delays how soon a metric summary reflects the latest events, never whether the eventual summary is correct.

**3. Why does this system distinguish "assignment" from "exposure" instead of just logging every `getVariant()` call?**
Because `getVariant()` gets called far more often than a variant is ever actually rendered — an eligibility check on a page a user never visits, a background job pre-computing state for a page load that never happens. Logging every call as if it were a real data point would dilute the analysis with users who were technically bucketed but never actually treated, biasing the very comparison the platform exists to make. Exposure logging fires only at the moment the variant is actually served, which is the population the significance test is supposed to describe.

**4. Why hash `(salt, experiment_id, user_id)` on the fly instead of storing a per-user assignment row?**
A stored assignment table needs a write (or at least a lookup) the first time every user hits every experiment — at the scale this platform runs at, that reintroduces exactly the per-check I/O the deterministic-hash approach exists to eliminate. The hash gets the identical property — same user, same variant, forever, for the life of the experiment — for free, computed locally, with zero storage, the same reasoning this guide's feature-flag design gives for the same question.

**5. How do you stop a PM from declaring a "winner" the moment the dashboard shows p < 0.05 on day 2 of a planned 4-week experiment?**
By making it structurally impossible for the dashboard to show a `"final"` verdict before then — `ExperimentAnalyzer.analyze()` (Module 02) checks a `PeekingGate` before it ever calls the significance test, and returns `"monitoring_only"` for any read before the pre-committed sample size or duration is reached. The false-positive-rate math behind requiring one clean look, not many, is Module 01's stated reason a fixed-horizon test can't be checked continuously; a mature version replaces the fixed-horizon test with a sequential one built to be checked safely at any time, rather than relying on a policy someone has to remember not to violate.

**6. What is Sample Ratio Mismatch, and why does it invalidate an entire experiment's results rather than just flagging a caveat?**
SRM is a configured traffic split (say 50/50) showing up in the data as something meaningfully different (say 55/45), detected by a chi-square goodness-of-fit test between observed and expected counts. It matters because a skewed split almost always means something broke in the assignment or logging pipeline — bot filtering removing more of one variant, a caching bug under-logging one arm's exposures — and if the two groups differ in ways beyond the treatment itself, any p-value computed over them is measuring a broken comparison, not the treatment's effect. `analyze()` (Module 02) returns `"untrustworthy"` instead of a number at all when SRM is flagged, because a caveat next to a wrong number still gets read as a number.

**7. What's a guardrail metric, and how is it different from the primary metric?**
The primary metric is what decides whether the experiment "wins" — conversion rate, revenue per user, whatever the team is actually testing for. A guardrail metric (p99 latency, error rate, crash rate) isn't being optimized for at all; it's being watched to make sure the treatment doesn't quietly break something else while winning on the metric it was designed to move. The Guardrail Monitor (Module 01) checks these on a tighter cadence than the primary-metric readout and can trigger an automatic halt on its own, independent of whether the primary metric looks good.

**8. Both this system and a feature-flag system need to bucket users into variants — what's actually different between them?**
The bucketing mechanism is genuinely the same trick (a deterministic hash mod 100 against a fixed range), and that's not a coincidence — it's the same problem. What's different is everything after the user is bucketed. A feature flag's job is done the instant a user is served a variant; this system's job only starts there, because it has to prove, using statistics over noisy human behavior, that what the user did afterward was actually caused by what they saw — which is why this design needs an exposure-logging distinction, a metric-join pipeline, a significance test, an SRM check, and a peeking discipline that a flag system has no reason to build at all.

**9. How would you prevent two concurrently running experiments on the same surface from interfering with each other?**
Not solved by this design as built — named explicitly in Module 01's "what you'd revisit" as mutually exclusive experiment layers. The fix is partitioning traffic into non-overlapping layers/namespaces (a second hash input alongside `experiment_id`) so a user assigned into experiment A on a given layer can't simultaneously be assigned into a conflicting experiment B on the same layer, while experiments on genuinely independent layers can still run concurrently over the same users without interference.

**10. Why is the metric pipeline a batch/stream join rather than a live query run against raw events every time someone opens the results dashboard?**
Because computing a trustworthy summary requires a global view — every exposed user's outcome, joined against their conversion events, aggregated per variant — and recomputing that from raw events on every dashboard load would mean scanning a growing multi-terabyte exposure and conversion history on every page view. The Metrics Aggregator computes it once, incrementally, as events arrive (Module 02's Welford-based running `(n, mean, variance)`), and the dashboard only ever reads the already-finalized result — the same separation of ingestion from serving this guide's [ad-click aggregation](../ad-click-aggregation/01-architecture-hld.md) pipeline draws for the identical reason.
