# Module 04 — Interviewer Q&A

**1. Why not just use a single Redis instance with `SET NX EX` as your coordination service?**
Because a single Redis node is itself a single point of failure — if it dies mid-lock, every client depending on it loses coordination at once, and a naive failover to a replica can hand the same lock to two clients if the replica hadn't caught up. [Distributed Locks](../../scalability-resilience/distributed-locks.md) names exactly this trade-off: a single-node lock is fine when a rare double-execution is cheap, but this case study is for when two simultaneous holders is a correctness violation, not an inefficiency — that's what justifies paying for a real consensus quorum (Module 01) instead.

**2. What happens when the coordination cluster's own leader crashes mid-write?**
The surviving replicas elect a new leader by majority vote. Any write that had reached a majority before the crash is guaranteed to survive in whichever replica becomes the new leader; any write that reached only a minority is discarded outright. A client waiting on that write sees a timeout or failure — never a write that appeared to succeed and then silently vanished (Module 01's Concurrent-User Handling table, and [Replication & Consensus](../../hld-building-blocks/replication-consensus.md)).

**3. Why does the cluster need an odd number of nodes — wouldn't 4 nodes tolerate more failures than 3?**
No — a majority of 4 is 3, exactly the same as a majority of 5 is 3. Going from 3 to 4 nodes buys zero additional fault tolerance (both still only survive 1 failure) while adding a full extra replica's storage, network, and fsync cost to every write. Going from 3 to 5 is the move that actually buys something (tolerating 2 failures instead of 1) — which is why real deployments jump between odd sizes and never land on an even one.

**4. How does a client acquire a fair lock without polling and without a thundering herd when it's released?**
Each contender creates a sequential ephemeral node under the lock's path; whoever holds the lowest-numbered node holds the lock. Every other waiter watches only the single node immediately before its own, not the lock-holder and not every other waiter — so a release triggers exactly one notification, to exactly the next waiter in line, and the order is strictly FIFO by creation time (Module 02's `acquire()` pseudocode).

**5. What happens to the lock if the holding client pauses (a long GC pause, a network partition) after acquiring it?**
Its session eventually stops heartbeating and expires, which deletes its ephemeral lock node automatically — the next-lowest waiter is granted the lock. The genuinely dangerous case is the paused client waking up later still believing it holds the lock and issuing a stale write downstream. The fix isn't at the lock at all — it's the fencing token (the sequence number the lock node was assigned at creation), passed to whatever resource the lock protects; that resource rejects any write carrying a token lower than the highest one it's already seen, which is exactly [Distributed Locks](../../scalability-resilience/distributed-locks.md)'s framing of this race, made concrete here by the sequence number the coordination service was already generating for free.

**6. Why is a watch fired only once — why not just keep the client permanently subscribed?**
Because a permanently-active watch on a popular path would mean every subscriber re-fires and has to be redelivered on *every single change* to that path — for the lock-queue recipe specifically, that would mean every waiter behind a released lock waking up on every release, not just the one waiter directly next in line. The one-shot contract keeps notification cost proportional to "watchers interested in this exact next change," which is what makes the sequential-node lock recipe scale to a deep queue instead of causing a stampede on every release (Module 03's reasoning on why watches are in-memory-only).

**7. Why can't you just store your application's actual data in this service instead of standing up a separate database?**
Because the mechanism that makes this service trustworthy — every replica holding the full tree in memory, every write fsynced and replicated to a majority before it's acknowledged — is only affordable at kilobytes-to-megabytes scale. At application-data volume, the same write path that gives you linearizability becomes a multi-second operation per write, and the in-memory-per-replica assumption stops fitting in RAM at all. This service is explicitly a small, strongly-consistent coordination primitive, never a general-purpose database (Module 00's framing, and Module 03's "why the small-data cap is enforced, not advisory").

**8. How does leader election among the coordination service's own replicas differ from the leader-election primitive it offers to its clients?**
These are two different mechanisms that happen to share a name, and conflating them is a common mistake. The service's *own* leader (Module 01) is elected via an internal consensus protocol (Raft/ZAB) among its own 3-7 machines, purely to decide who gets to order writes to the znode tree — clients never see this election directly. The leader-election *primitive* clients use (Module 02) is an ordinary application of the sequential-ephemeral-node lock recipe, running entirely on top of that already-consistent tree — it's client-side logic, not a second server-side consensus mechanism. The first is the substrate; the second is a recipe built on it.

**9. Why don't reads need to go through the leader or a majority the way writes do?**
Because most coordination reads (checking a config value, checking your position in a lock queue) don't need a guarantee stronger than "my own reads never go backward in time" — sequential consistency, not linearizability (cross-ref [Consistency Models](../../hld-building-blocks/consistency-models.md)). Serving reads from whichever replica a client is already connected to, straight from memory, decouples read scalability entirely from the write-consistency mechanism. A client that genuinely needs a guaranteed-current read can call `sync()` first, paying the latency cost only when it actually needs to.

**10. If read load (config lookups, watches) grew 100x, how would you scale this, given that adding voting replicas doesn't help?**
Add non-voting **observer** replicas — nodes that replicate the leader's committed write stream and serve reads and watches, but are never counted toward the write quorum. This adds read capacity in direct proportion to how many you add, with zero effect on write latency, which is the opposite of the voting cluster's trade-off (Module 01's Load Handling): growing the voting set slows writes down, but growing the observer set only ever helps.
